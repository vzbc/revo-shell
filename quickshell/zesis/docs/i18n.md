# i18n

UI strings go through the `I18n` singleton (`I18n.qml`, root of the repo) instead of being
literal QML strings, so the shell can be used in a language other than English.

## Structure

```
i18n/
  manifest.json       # languages + the list of domains to load
  en/
    common.json        # shared words: Cancel, Save, Search...
    settings_chrome.json
    user.json
    <domain>.json       # one per feature area, see below
  pt_BR/
    common.json
    ...                 # same domain files, translated
```

Each domain is a **flat** JSON object (no nesting): `{"title": "User", "changeAvatar": "Change avatar"}`.
Domains roughly mirror `widgets/<Folder>` - e.g. `widgets/bluetooth` -> `i18n/en/bluetooth.json`. Settings
panels reuse the `navId` already used for routing in `SettingsPanel.qml` (`appearance`, `bar`, `clock`,
`user`...) as their domain name, so the two stay easy to cross-reference.

This split (many small files instead of one big `en.json`) is deliberate: two people adding strings to
different panels never touch the same file, so translation work merges the same way the rest of the
codebase does.

## Adding a string

1. Add the English key to `i18n/en/<domain>.json` (create the file/domain if it doesn't exist yet).
2. Add the same key, translated, to every other language's `i18n/<lang>/<domain>.json`. If you don't
   have a translation yet, that's fine - `I18n.t()` falls back to English automatically.
3. If it's a new domain, add its name to the `domains` array in `i18n/manifest.json`.
4. In the `.qml` file, replace the literal with `I18n.t("<domain>.<key>")`.

For strings built with placeholders (counts, percentages, names...), use positional `%1`/`%2` markers
in the JSON value and pass an array:

```qml
// i18n/en/battery.json: { "percent": "%1%" }
text: I18n.t("battery.percent", [level])
```

Positional placeholders let a translation reorder them (`"%2 de %1"` vs `"%1 of %2"`) without touching QML.

Never translate: icon glyph strings (Material Icons / Nerd Font code points), color hex values, file
paths, and brand/product names (AirPods, zesis, Bluetooth, Wi-Fi as a proper noun, etc. - use judgement).

## Adding a language

1. Add `{ "code": "xx_YY", "englishName": "...", "nativeName": "..." }` to `i18n/manifest.json`'s
   `languages` array. `code` should match the OS locale format (`Quickshell.env("LANG")` etc.), e.g.
   `pt_BR`, `de`, `ja`.
2. Create `i18n/xx_YY/` with the same domain files as `i18n/en/` (start by copying `en/` and translating
   values - missing files/keys just fall back to English, so this can be done incrementally).
3. Run `python3 scripts/i18n-check.py` to see exactly which keys are still missing.

No QML changes needed - the language shows up in the Settings / Account / User switcher automatically,
and gets picked up by auto-detection if it matches the user's `LANG`/`LC_*` (or `Qt.locale()` as a last
resort).

## How resolution works

`I18n.language` is either the user's manually pinned choice (persisted to
`~/.cache/zesis/locale.json`, survives restarts) or, by default, `"system"` - which resolves against
`LC_ALL` -> `LC_MESSAGES` -> `LANG` -> `Qt.locale().name`, first trying an exact match against shipped
languages, then a base-language match (`pt_BR` env with only a `pt` build shipped still matches), then
hard-falling back to English.

`I18n.t(key, args)` looks the key up in the effective language; if missing, in English; if missing
there too, it returns the key itself (so an untranslated string is visibly obvious rather than silently
blank) - `scripts/i18n-check.py` is the actual way to find gaps, this is just a visible last resort.
